# Agentic Life World Studio｜產品規劃提案

**狀態：待作者確認。** 本文件是重新規劃的需求提案，不是已完成能力，也不是開發授權。作者確認產品、流程與驗收範圍後，才設計新版資料契約並開始實作。

## 1. 成品與產品目標

作者提供一份原作，建立一個可持續出版的異世界影像旅行網站。讀者進入網站，是跟隨觀察者探索世界：看見新景象、生命與地方，閱讀短篇旅行見聞，逐步形成對這個世界的認識。後續可訂閱每週明信片，並把既有影像與文字集結成美術集。

私人 Studio 是作者的創作與營運工作台。AI 負責讀懂原作、提出可用的世界創作設定，作者負責確認核心、延伸界線與呈現風格。網站在核准的範圍內自主出版，持續將成果與異常回報 Studio。

「通用」指相同產品流程可以處理不同類型、長度及視覺風格的原作，不以範例的專名、災變、年代、人物或媒介寫死提示詞及結構。

### 萃取的唯一判準

這項資訊會改變影像中可見的內容、旅行文字的表達，或後續創作的許可範圍嗎？不會，就不列為世界初始化的工作。原作可以保留全文，但不需要將全部情節轉成資料欄位。

## 2. 重建方式與取捨

| 方案 | 做法 | 取捨 |
|---|---|---|
| **建議：重新設計產品及流程，保留必要基礎資源** | 原作到出版的資料契約、Agent 輸入輸出及 Studio 操作重新設計；既有帳號、網域、secret 與儲存資源逐項確認後使用 | 不用重設授權，也不讓舊流程限制產品；需要先完成新的端到端驗收 |
| 全部基礎設施重建 | 新建儲存、帳號設定與部署環境 | 可完全隔離，但增加授權、搬遷及重複維運成本，對讀懂原作沒有直接幫助 |
| 在既有流程修補 | 保留原本步驟，持續調整欄位與文案 | 改動較少，但不能充分解決流程本身與作者需求不符的問題 |

建議採第一案。保留資源不代表沿用舊解析、舊問答、舊核准或舊資料契約。既有輸入不自動成為新設定，也不自動重跑；資料重設與搬遷另外明確界定，不刪除作者原檔。

## 3. 先從網站反推需要的設定

以下六項是 AI 閱讀與生成的框架，也是作者可理解的確認摘要；不要求作者逐欄從空白開始填寫。每項允許「原作未說明」或「不影響本次創作」，但必須說明可採用的方向與適用界線。

| 項目 | 應產生的內容 | 何時需要作者決定 |
|---|---|---|
| 世界基本樣貌 | 名稱、年代、造成現況的主要背景、可見文明與建築、空氣與環境、生命外觀；只取影響影像與見聞的內容 | 原作出現會導致不同成品的實質矛盾；必要設定完全缺少且無法安全推導 |
| 視覺風格 | 從原作圖像及文字判斷媒介、色彩、光線、材質、尺度、氣氛；區分世界事實與表現手法 | 圖片風格互相衝突，或作者需要指定最終採用的方向；最後必須確認實際試稿 |
| 觀看者、敘述與受眾 | 誰在觀察、是否出鏡、文字聲音、讀者輪廓與內容尺度；AI 先提出符合原作的建議 | 使用原作人物或新觀察者會改變授權範圍、劇情或網站定位 |
| 旅程時間與揭露 | 探索發生的時期、時間是否推進，以及劇透或特定事件的揭露限制 | 旅程位置無法判斷，且不同選擇會改變世界景象或公開資訊 |
| 命名與多語原則 | 世界名稱、少量重要專名、領域與生命的命名語感、翻譯或音譯原則 | 同一重要名稱有不同版本，或新命名規則會影響作品辨識 |
| 忠實補全的邊界 | 核心不可改動之處、可合理衍生的景觀／生命／小事件、禁止內容及需要重新提案的情形 | 初始化時，作者明確同意 AI 可衍生的範圍；不得由沉默或系統預設取得授權 |

領域與物種可在原作已明示時納入；其餘在核准的範圍內隨探索逐步形成，不強迫初始化建立完整清單。日期、日誌編號、網站分類、版型與更新頻率是出版設定，不應變成原作解析疑義。

## 4. Studio 的實際使用流程

### 4.1 匯入原作

作者貼文字、上傳 Word／PDF 或提供網址，可附參考圖。系統顯示實際讀到的標題、文字摘要與圖片縮圖，讓作者確認匯入的是正確內容。單張圖片須接受至少 5 MiB，其他總量上限於契約設計時按部署限制明示，不沿用任意的舊限制。

網址沒有讀取權限、掃描檔需要辨識或圖片無法取得時，直接指出無法取得的項目及替代操作。不能把匯入不完整假裝成已讀完，也不能讓作者回答世界設定來掩蓋讀檔故障。

### 4.2 AI 先提出一份可用草稿

閱讀結果直接形成六項簡明摘要、一個有依據的視覺方向，以及必要時的作者裁定。頁面預設顯示可閱讀的結果與「修改／與 AI 討論／確認設定」，技術依據置於可展開的來源資訊。

不列全文人物關係、物品百科、逐句引文疑義，也不為湊足題數而提問。原文定位與格式驗證留在系統內部；模型輸出不合格式，由系統校正或重試。

### 4.3 作者裁定必須可以直接回答

每一題都必須包含：

1. **具體問題：**明確指出要作者決定的事項。
2. **為何需要決定：**說明會如何影響影像、文字或創作範圍。
3. **依據：**原作相關段落／圖片；若原作未提及，直接寫明。
4. **AI 建議：**提出一個可採用的答案與理由，標示為建議。
5. **操作：**採用建議、選其他方向，或自行補充；不先替作者送出。

若問題不會改變成品，不提問。若一題已有建議，不能只留下空白輸入框。作者回答後，AI 更新設定並標出改動，不能只保存一段無法知道用途的留言。

### 4.4 視覺校準與一次明確啟用

根據草稿與參考圖產生實際試稿，作者可以看圖並提出具體調整。試稿數量與題材只取足以驗證畫風、環境及生命外觀的組合；原作沒有生命描寫時不強造生物來完成流程。

作者可以先儲存設定確認，再調整視覺。最後在同一個「啟用」頁面檢視設定摘要、核准的補全範圍與試稿，再明確啟用。所有確認綁定內容版本；更改相關內容後顯示需重新確認之處，不可沿用失效核准，也不讓作者到不同頁面尋找下一步。

## 5. Agent 分工與調度

Agent 是各自有明確輸入、輸出及限制的工作角色。模型不能自行取得新權限、核准世界或發布。調度器依持久化狀態執行，不能依賴一段聊天記憶維持一致性。

| 角色 | 輸入 | 輸出與責任 |
|---|---|---|
| 世界導演 | 原作、圖片索引、作者補充 | 篩選對成品有用的核心，形成六項草稿；辨別原文明示、推導、補全建議；只整理必要裁定 |
| 視覺導演 | 草稿與實際取得的原作圖片 | 定義可生成的風格方向、提出試稿；沒有讀到像素就不得宣稱已分析配圖 |
| 忠實度審核者 | 草稿、對應原文與圖片、補全範圍 | 獨立查核是否誤讀或超出原作；能由依據修正的直接修正，實質矛盾才交作者 |
| 元素管理者 | 核准設定、既有元素及待生成內容 | 查重、沿用穩定名稱與外觀、提出新元素；拒絕範圍外變更 |
| 出版者（後階段） | 核准設定、元素、既有旅程紀錄 | 產生探索提案、影像與見聞，審查後形成公開版本，回報 Studio |
| 多語編輯（後階段） | 核准的公開內容與名稱表 | 產生中／英／日版本，維持名稱及語意一致，整理真正需要校準的譯名 |

第一階段先實作世界導演、視覺導演、忠實度審核及最小元素管理。原文過長可以分段閱讀，但分段只是內部處理，不產生成百個作者工作項。獨立審核必須能讀到原始依據，不能只檢查另一個 Agent 的摘要。

流程：匯入完成 → 世界草稿 → 視覺方向／忠實度查核 → 必要作者裁定 → 試稿與調整 → 設定及視覺確認 → 啟用。技術重試與作者裁定是不同狀態；前者絕不能自動轉成後者。

### 技術邊界

推理採 Meta `muse-spark-1.3` 的相容 API，影像採 Muse Image；模型名稱與實際 endpoint 在實作時以官方契約驗證，不任意改供應商。Multi-agent 調度由部署端掌握工作狀態、工具權限及執行順序，所有角色使用 Meta 模型，不能用另一個供應商的 Agent 服務代替核心調度。

建議沿用 GitHub 與 Cloudflare 的部署基礎，以及 React／TypeScript Studio、部署端 API、D1 中央資料、R2 原作／影像儲存與 Queue 背景工作的資源分工。這是資源選擇，不代表沿用現有程式；新的模組邊界、契約及失敗處理在作者核准提案後重新設計。

## 6. 最小資料架構

| 資料 | 目的與必要內容 |
|---|---|
| 原作與參考圖 | 原始檔、擷取文字、圖片、來源定位、內容雜湊及實際讀取狀態；私人保存 |
| 世界設定版本 | 六項設定；各重要設定的來源類別：原文明示／有依據的推導／待核准補全／作者裁定 |
| 裁定與核准 | 具體題目、AI 建議、作者答案、對應版本、明確確認時間；補全核准不可與核心來源混淆 |
| 視覺設定與試稿 | 參考圖、風格描述、生成圖、作者調整、對應世界版本及核准狀態 |
| 中央元素 | 穩定 ID、種類、來源或衍生關係、特色、外觀、所屬區域（適用時）、中英日名稱／公開定義、使用狀態 |
| 出版與旅程紀錄 | 已發現元素、實際發生的小事件、行程位置／時間、已發布內容及語系版本，避免重複與自相矛盾 |
| 執行與稽核 | 工作狀態、可恢復進度、用量、錯誤及重試、內容修訂與發布紀錄；不作作者必填欄位 |

元素 ID 不隨翻譯改變。未知名稱可以待命名，已有外觀不得在下一篇無故改寫。核心設定與補全提案尚未核准時不得進入已啟用設定。

公開網站只讀取專用的已發布資料，不直接序列化私人世界文件。原作全文、補全標記、作者裁定、prompt、模型資訊及操作稽核不進入公開 API、HTML、SEO、替代文字或其他公開輸出。

本提案先確認資料責任，不預先把舊 schema 當作新版本基礎。確認後再交付可執行契約、migration 與 API 設計。

## 7. 失敗處理與可恢復性

- **系統能處理：**格式不符、引文定位、暫時性網路或模型回應問題，先自動處理，重試有次數及成本上限，保存成功進度。
- **需要作者操作：**來源權限不足、檔案毀損、缺少需要指定的參考圖，說明具體缺少什麼，提供更換／補傳／重試操作。
- **需要作者創作裁定：**只限第 4.3 節的可回答問題，不與技術失敗混在一起。
- **重試仍失敗：**明確顯示哪個階段未完成、已保存什麼，以及「重試／換來源／暫停」；不出現「請補充你的理解」之類無題目的問答。
- **安全恢復：**避免重複工作與重複提交；可能已計費但未能確認結果時，記錄不確定狀態，不宣稱完全沒有費用。取消工作後不得自動恢復。

## 8. 分階段交付與驗收

### 第一階段：只驗證從原作到可啟用的世界

交付匯入與讀取確認、六項 AI 草稿、必要作者裁定、參考圖與實際試稿、同頁確認及啟用，以及支撐一致性的最小中央元素資料。

驗收：

- 使用兩篇題材與視覺風格不同的中性測試文本，不修改提示詞或加入作品特例，就能完成相同流程。
- 摘要聚焦對影像與見聞有用的設定，沒有無關人物／物品清單；資訊足夠時不提問。
- 作者能從單一確認頁知道目前進度、待處理事項及下一步；每一個提問都有依據、建議及可操作答案。
- 單張 5 MiB 圖片能成功匯入；有圖片與沒有圖片的原作都能如實處理。
- 作者看到實際試稿，修改與核准的版本一致；未經本人確認不能啟用核心設定或補全。
- 對格式錯誤、圖片讀取失敗、暫時性服務失敗、重試及取消進行故障驗證，不要求作者替系統排除技術錯誤。
- 不強制要求元素清單齊全，也不讓後續翻譯與營運設定阻擋此階段驗收。

### 第二階段：從核准世界到公開網站

建立英文網站私人預覽，經作者發布後取得公開網址；加入中／英／日名稱及翻譯校準。驗收公開投影、語系切換、名稱一致、修改後舊翻譯失效，以及 dev／正式環境資料契約一致。

### 第三階段：持續探索與回報

由作者設定出版頻率、主題偏好及成本上限；系統在已核准範圍內探索，通過忠實度、重複及視覺檢查後出版，將進展回報 Studio。範圍外內容留在提案，不直接公開。驗收至少連續三輪出版，確認元素外觀、名稱、事件與時間連貫。

### 第四階段：訂閱與美術集

使用已發布素材製作每週明信片與美術集；寄送採事件驅動、退訂篩選與持久化冪等，另行確認產品、寄送與輸出規格。

## 9. 開發與發布界線

本提案核准前不寫新功能、不產生 migration、不變動模型調度，也不發布新程式。README 只保留產品說明及目前規劃入口，不放開發事故、修補歷程或歷史發布清單。

核准後先完成第一階段的資料契約、API、頁面操作與測試案例；以一個中性短文本走通端到端，再測長文本、圖片與故障，最後測第二個不同題材。不能以模型呼叫成功、測試數量或建置通過代替作者實際使用驗收。

程式碼經 GitHub 觸發 Cloudflare 部署；涉及資料契約時同步處理 dev／正式 migration、API 與前端，交叉驗證 deployed code、schema、live behavior 與 audit。純文件不觸發完整 CI／正式部署，不因重寫文件而重設歷史版號。
